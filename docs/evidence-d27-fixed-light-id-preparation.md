# D27 fixed-light-ID loop bisection: preparation

## Question

D26 proves that the square artifact requires entry into the two pixel shaders'
tiled dynamic-light loop. D27 asks whether the real `t10` light IDs/list are
required, or whether the artifact can still be generated by the per-light data
and calculations when every iteration evaluates one controlled valid light.

## Exact change

D27 preserves:

- the real packed `t9` per-tile count and start offset;
- entry into the per-light loop;
- the original number of loop iterations;
- the `t10` fetch instruction itself;
- all per-light data fetches, branches, calculations, accumulation, and final
  render-target writes.

It changes only the scalar ID extracted from the `t10` fetch to constant `1`.
`ComputeLightsIndices` writes `GlobalInvocationID.z` as its light ID and the
consumer treats zero as a sentinel, so `1` is the first non-sentinel ID.

For each shader, the generator replaces one five-word `OpCompositeExtract`
with a five-word `OpBitwiseOr(1, 0)`. It verifies the complete instruction
signature and exactly one match. Each output differs from the original in four
bytes and passes Vulkan 1.3 validation.

## Interpretation

- **Grid disappears while some dynamic lighting remains:** the actual `t10`
  IDs/list interpretation is required. Inspect its produced values, R16 view,
  bounds, and producer/consumer contract.
- **Grid remains, possibly with changed intensity/color:** actual IDs are not
  required. Focus on real tile counts, repeated accumulation, the resolved
  light-1 data, and translated per-light math/control flow.
- **Scene is not classifiable:** refine to a one-light-per-nonempty-tile variant
  rather than treating missing or extreme lighting as a result.

D27 remains a developer diagnostic and is not a final fix or upload candidate.
